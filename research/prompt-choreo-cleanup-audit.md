# Choreo Integration Cleanup Audit

## Context

This is an FRC swerve drive robot codebase on the `choreo-template` branch. We recently migrated from a custom path infrastructure (SplinePath, VelocityProfile, React editor) to Choreo for trajectory design, with arc-length re-parameterization for distance-based following.

The migration added:
- `FollowablePath` interface (`utils/path/FollowablePath.java`)
- `ArcLengthTrajectory` — Choreo adapter, re-parameterizes t→s (`utils/path/ArcLengthTrajectory.java`)
- `AutoPath` enum — type-safe alliance-aware path references using `ChoreoTraj` (`utils/path/AutoPath.java`)
- `LQRFollower` — LQR tracking controller prototype (`commands/LQRFollower.java`)
- ChoreoLib 2026.0.3 vendordep (`vendordeps/ChoreoLib2026.json`)
- Simplified `FollowPath` (`commands/FollowPath.java`) and `AutoCommands` (`autonomous/AutoCommands.java`)

We deleted all legacy path infrastructure (SplinePath, CubicSegment, VelocityProfile, PathData, Paths.java) and many unused subsystems (Shooter, Turret, Intake, Hopper, Climber, Superstructure, etc.).

### Choreo Code Generation

Choreo auto-generates two files that we should NOT modify but SHOULD leverage:

1. **`autonomous/ChoreoTraj.java`** — A record with:
   - Static constants for every trajectory (e.g., `ChoreoTraj.NewPath`)
   - Fields: `name`, `segment`, `totalTimeSecs`, `initialPoseBlue`, `endPoseBlue`
   - `ALL_TRAJECTORIES` map for runtime lookup by name
   - `segment(int)` for trajectory segments
   - `asAutoTraj(AutoRoutine routine)` — ChoreoLib helper (we don't use this since we do distance-based following, not Choreo's time-based AutoRoutine system)

2. **`autonomous/ChoreoVars.java`** — Variables and poses defined in Choreo's GUI expression system. Currently has an empty `Poses` inner class.

Our `AutoPath` enum references `ChoreoTraj` constants directly — deleting or renaming a trajectory in Choreo regenerates `ChoreoTraj.java`, and any stale `AutoPath` entry becomes a compile error.

## Your Task

Do a thorough audit of the ENTIRE codebase. Read every Java file. Check for:

### 1. Dead Code and Stale References
- Imports that reference deleted classes or packages
- Methods, fields, or constants that reference deleted subsystems or old path infrastructure
- Unused imports, unused private methods, unused fields
- Any file that exists but is never referenced from anywhere
- Constants or config values that only made sense for deleted subsystems

### 2. Choreo Library & Code Generation Alignment
- Read the ChoreoLib vendordep (`vendordeps/ChoreoLib2026.json`) to understand what version we have
- Read `ChoreoTraj.java` and `ChoreoVars.java` — these are generated by Choreo, DO NOT modify them
- Check if we're using ChoreoLib's built-in utilities where we could be (e.g., `Choreo.loadTrajectory`, alliance flipping, event markers)
- Check if ChoreoLib provides trajectory utilities we're reimplementing manually (especially in `ArcLengthTrajectory`)
- Verify `AutoPath` correctly uses `ChoreoTraj` constants (not raw strings)
- Check if `ChoreoTraj.initialPoseBlue` / `endPoseBlue` can simplify pose reset logic in autos
- Check if `ChoreoTraj.totalTimeSecs` or `segment()` support could simplify anything
- Check if `ChoreoVars.Poses` could replace any hardcoded field positions
- Verify vendordep is up to date and correctly configured in build.gradle
- Check if Choreo's `AutoRoutine`/`AutoTrajectory` system offers anything we should use alongside our distance-based following (probably not, but verify)

### 3. Simplification Opportunities
- Can any file be further simplified now that we have ChoreoTraj code generation?
- Are there utility classes that are now over-engineered for their single use case?
- Are there abstractions that exist for hypothetical future use but add complexity now?
- Can `AutoCommands.java` be simplified further? Could `followPathWithActions` leverage ChoreoTraj event markers more directly?
- Is `RotationSupplier` still needed or can heading just come from FollowablePath?
- Is `ProjectionResult` still the right abstraction?
- Is there overlap between `AutoPath` and what `ChoreoTraj` already provides? Can we reduce boilerplate?

### 4. Consistency Check
- Do `FollowPath` and `LQRFollower` handle edge cases the same way (path completion, projection bounds, initial state)?
- Are logging namespaces consistent?
- Are builder method patterns consistent between the two controllers?
- Does `AccelerationLimiter` still make sense with the new controllers or does it have dead code paths?

### 5. Build and Config
- Check `build.gradle` for stale dependencies or plugins
- Check vendordeps/ for unused vendordep files
- Check deploy/ for stale files (old pathplanner, etc.)
- Check if there are any test files that reference deleted code
- Verify Choreo project file (`Choreo.chor`) exists at project root

## Rules
- Read files before suggesting changes
- NEVER modify `ChoreoTraj.java` or `ChoreoVars.java` — they are Choreo-generated
- If you find something to fix, fix it — don't just list it
- Run `./gradlew build` after changes to verify
- Keep changes minimal — don't refactor working code for style, only fix actual issues
- If something is borderline (might be needed later), leave it and note why
